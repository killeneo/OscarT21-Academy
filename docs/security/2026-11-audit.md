## Executive summary

The authentication and authorization core is in good shape. SQL injection, XSS, open redirects, CSRF, session fixation,
IDOR, mass assignment, prototype pollution, cache leakage of personalised pages and the race conditions that were
tested (password-reset token, duplicate sign-up, rate-limit counters, specialist review state machine) were **not
exploitable**. 58/58 black-box security tests pass on both the dev server and the production build.

One **confirmed** issue matters before any self-hosted deployment: when `TRUSTED_IP_HEADER` is not set, all clients
share one per-IP rate-limit bucket, so 30 failed logins from anyone block logins for everyone for 15 minutes, and
10 sign-ups per hour block registration site-wide (**F-01**). This is a side effect of the IP-spoofing fix in PR #11.
On Vercel it does not apply (`VERCEL=1`).

The main **design risk** is the third-party Telegram Login Widget script, which runs with full DOM access on the
login and sign-up pages, next to the password field (**F-02**).

Everything else is low severity, informational, or a residual risk inherent to e-mail-based accounts.

**Overall assessment:** suitable for continued MVP development; fix F-01 before self-hosting and F-02 before launch.
No AI/LLM features, file uploads, payments, GraphQL, WebSockets or webhooks exist yet, so those modules were not
applicable (see "Coverage").

## Findings

### F-01 — Shared per-IP rate-limit bucket enables site-wide denial of login and sign-up

- **Category:** Business logic / Improper rate limiting
- **OWASP:** A04:2021 Insecure Design; API4:2023 Unrestricted Resource Consumption
- **CWE:** CWE-799 Improper Control of Interaction Frequency; CWE-400
- **Severity:** Medium; High for a self-hosted deployment without the header
- **CVSS 4.0 vector (estimate):** `AV:N/AC:L/AT:P/PR:N/UI:N/VC:N/VI:N/VA:H/SC:N/SI:N/SA:N`. `AT:P` because it requires a deployment without `VERCEL=1` or `TRUSTED_IP_HEADER`. No exact score is given; compute it with the FIRST calculator once the hosting is fixed.
- **Affected component:** `web/lib/auth/client-ip.ts` (`clientIp` returns `"unknown"`) combined with the per-IP limits in `app/api/auth/{login,register,password/forgot,password/reset,telegram,verify/*,google/callback}`
- **Description:** To stop IP spoofing, `clientIp()` trusts no header unless one is configured. Without configuration every request maps to the same key (`login:ip:unknown`, `register:ip:unknown`, …), so a per-IP limit becomes a **global** limit. Login allows 30 attempts per 15 minutes and sign-up 10 per hour across the whole site.
- **Evidence (local production build, no `TRUSTED_IP_HEADER`):** 30 failed logins for 30 random non-existent e-mails (all `401`), then the correct password for a different test account → `429`. 10 sign-ups → `201`, the 11th sign-up by anyone → `429`. The PoC script is `docs/security/poc/poc.mjs`, check 1.
- **Preconditions:** Production deployment outside Vercel, or behind a proxy, with `TRUSTED_IP_HEADER` unset. A warning is logged, but nothing enforces the configuration.
- **Security impact:** An unauthenticated attacker can keep login unavailable for all users with about 2 requests per minute, and block registration with 10 requests per hour. Legitimate traffic alone would also hit the sign-up cap.
- **False-positive considerations:** Not applicable on Vercel (`x-vercel-forwarded-for` is used). The behaviour was reproduced, not inferred.
- **Safe validation method:** Run the production build locally without `TRUSTED_IP_HEADER`, send 31 failed logins with distinct e-mails, then log in with a test account.
- **Remediation:**
  1. **Fail fast:** in production, refuse to serve auth routes (or refuse to start) when neither `VERCEL=1` nor `TRUSTED_IP_HEADER` is set.
  2. Support an explicit `TRUSTED_IP_HEADER=none` that **skips** per-IP buckets instead of sharing one. Per-account and per-e-mail limits plus the scrypt concurrency gate still apply.
  3. Optionally keep a much higher global safety cap (for example 1 000 per 15 minutes) that is clearly labelled as global.
  4. Add the configuration check to the deployment checklist (`docs/ci-cd-setup.md`).
- **Retest:** Repeat the PoC with each configuration (`VERCEL=1`, `TRUSTED_IP_HEADER=x-real-ip`, `none`, unset). The unset case must fail fast; the others must not block an unrelated user.
- **Confidence:** High

### F-02 — Third-party Telegram widget script runs next to the password field

- **Category:** Client-side / Third-party JavaScript / Software supply chain
- **OWASP:** A08:2021 Software and Data Integrity Failures
- **CWE:** CWE-829 Inclusion of Functionality from Untrusted Control Sphere
- **Severity:** Medium (low likelihood, high impact)
- **CVSS:** not scored; it depends on a third-party compromise
- **Affected component:** `web/components/telegram-login.tsx`, which loads `https://telegram.org/js/telegram-widget.js?22`; the CSP allows `https://telegram.org` in `script-src`
- **Description:** When Telegram is configured, the widget script is injected into the login and sign-up pages. It runs in the page's origin with full DOM access, including the e-mail and password inputs and the hidden consent field. SRI is not possible because Telegram changes the file in place.
- **Evidence:** Code review: `TelegramLogin` is rendered unconditionally in `AuthForm` when `telegramBot` is set, and the script is appended to the page DOM. No exploit was attempted: the third party is out of scope.
- **Preconditions:** `telegram.org` (or its delivery path) is compromised, or serves malicious code.
- **Security impact:** Credential capture on the login and sign-up pages, and session-riding actions on those pages.
- **False-positive considerations:** This is a design risk, not a defect in our code. The likelihood is low.
- **Remediation (in order of preference):**
  - Load the widget only after the user explicitly clicks "Войти через Telegram", on a **separate page without password fields** (for example `/[lang]/login/telegram`).
  - Or move to Telegram's newer OpenID Connect login, a redirect flow with no third-party script on our pages.
  - Keep `script-src https://telegram.org` only on that page through per-route headers.
- **Retest:** The login and register HTML must not reference `telegram.org` scripts. The CSP of those pages must not allow `telegram.org`.
- **Confidence:** Medium

### F-03 — CSP allows `'unsafe-inline'` scripts

- **Category:** Security misconfiguration (defence in depth) · **OWASP:** A05:2021 · **CWE:** CWE-1021 / CWE-79 (mitigation weakness)
- **Severity:** Low (Informational while no XSS sink exists)
- **Affected component:** `web/next.config.ts`
- **Description:** `script-src 'self' 'unsafe-inline' https://telegram.org`. This is needed for Next.js inline bootstrap scripts on statically rendered or PPR pages, so nonces are not possible. If an HTML injection bug appears later, the CSP would not stop script execution.
- **Evidence:** Production response header (PoC check 8). The only `dangerouslySetInnerHTML` is a static string in `app/[lang]/layout.tsx`. React escaping was verified with hostile display names and search terms (security tests).
- **Remediation:** Keep the dangerous-sink count at one; add an ESLint rule forbidding `dangerouslySetInnerHTML` outside the layout. Re-evaluate nonces or hashes for authenticated, dynamically rendered routes (`/account`, `/onboarding`) using per-route headers. Consider Trusted Types (`require-trusted-types-for 'script'`) in report-only mode.
- **Confidence:** High (configuration), no exploit

### F-04 — `/password/forgot` timing differs for existing accounts

- **Category:** Authentication / Account enumeration · **OWASP:** WSTG-IDNT-04 · **CWE:** CWE-208 Observable Timing Discrepancy
- **Severity:** Low (today); would rise once a real mail provider is called synchronously
- **Affected component:** `web/app/api/auth/password/forgot/route.ts`
- **Description:** For an existing active user the route runs `issueToken` (a transaction) and `sendPasswordResetEmail` before answering; for an unknown address it answers right after one lookup. The response bodies are identical.
- **Evidence:** Local production build, 15 samples each with limits reset between samples: median **15.6 ms (existing) vs 13.6 ms (unknown)**, about 2 ms difference. Mail went to the console here; an HTTP mail API typically adds 100 ms or more.
- **Preconditions:** Many samples per address. The per-address limit (3 per hour) and per-IP limit (10 per hour) slow down measurement. Network jitter hides a 2 ms difference on the internet, but not a 100 ms one.
- **Remediation:** Respond first and send the mail through a background job or queue; CLAUDE.md already requires background jobs for e-mail. Do the same for the "account exists" notice in `/register`.
- **Retest:** Repeat the timing PoC with the real provider wired in; the medians must differ by less than about 1 ms.
- **Confidence:** Medium

### F-05 — Origin check trusts client-supplied `X-Forwarded-Host`

- **Category:** CSRF defence / Host header handling · **CWE:** CWE-346 Origin Validation Error
- **Severity:** Informational
- **Affected component:** `web/lib/auth/http.ts` `hasSameOrigin()`
- **Description:** The expected host is `x-forwarded-host ?? host`. A non-browser client can send `Origin: http://evil.example` together with `X-Forwarded-Host: evil.example` and pass the check.
- **Evidence:** PoC check 9: login with a foreign Origin plus a matching `X-Forwarded-Host` passed the Origin check (`401` from the credential check, not `403`).
- **Why it is not exploitable as CSRF:** A victim's browser cannot set `X-Forwarded-Host` on a cross-site request without a CORS preflight, and the app sends no CORS headers (no `Access-Control-Allow-Origin`, verified). A non-browser attacker does not need CSRF.
- **Remediation:** Compare `Origin` with the configured public origin (`NEXT_PUBLIC_SITE_URL`) and trust `x-forwarded-host` only under the same trusted-proxy setting as F-01.
- **Confidence:** High

### F-06 — Reset and verification token stays in the URL and browser history

- **Category:** Sensitive data exposure · **CWE:** CWE-598 Use of GET Request Method With Sensitive Query Strings
- **Severity:** Low
- **Affected component:** `web/components/recovery-pages.tsx`, `/[lang]/reset-password`, `/[lang]/verify-email`
- **Description:** The single-use token arrives as `?token=…` (necessary for e-mail links) and is never removed from the address bar. It stays in history, synced browser history and screenshots until used or expired (1 h / 24 h). Mitigations already in place: `Referrer-Policy: no-referrer` on these pages, `noindex`, POST-only consumption, single use, short TTL, and no third-party scripts on these pages.
- **Remediation:** After reading the token on the client, call `history.replaceState(null, "", location.pathname)`, or move it into the URL fragment.
- **Confidence:** High (behaviour), low impact

### F-07 — No idle session timeout; long absolute lifetime; no session overview

- **Category:** Session management · **ASVS:** V3.3.1 / V3.3.2 · **CWE:** CWE-613 Insufficient Session Expiration
- **Severity:** Low
- **Description:** Sessions live 14 days regardless of activity. "Log out on all devices" exists, but there is no list of active sessions and no idle timeout.
- **Remediation:** Add a `last_seen_at` with a sliding idle timeout (for example 7 days, or shorter for moderator and admin roles when those exist), and a session list in the account page. Require re-authentication for future high-risk actions (e-mail change, deletion, role management).
- **Confidence:** High

### F-08 — `rate_limits` rows are never cleaned up

- **Category:** Resource consumption · **CWE:** CWE-770
- **Severity:** Low
- **Affected component:** `web/lib/auth/rate-limit.ts`
- **Description:** Every new key (per IP, per hashed e-mail) creates a row that is reset but never deleted. Unknown e-mails in `/forgot` and `/login` create rows too. Over time, or under abuse, the table grows without bound. `sessions`, `auth_replay` and `trusted_devices` are cleaned; `rate_limits` is not.
- **Remediation:** Periodically run `DELETE FROM rate_limits WHERE reset_at < now() - interval '1 day'`, either in the same opportunistic way as sessions or as a scheduled job.
- **Confidence:** High

### F-09 — E-mail aliases and IDN forms create separate accounts

- **Category:** Identity · **Severity:** Informational
- **Description:** E-mails are only trimmed and lower-cased. `a.lice+x@gmail.com` and `alice@gmail.com` (one Gmail mailbox), or an IDN domain in Unicode and in punycode, become different accounts with separate per-account rate-limit budgets. There is no security boundary violation, since each account still needs its own credentials. It does matter for Sybil resistance of reviews and other one-account-per-person rules later.
- **Remediation:** When reviews or other per-person limits arrive, add a canonical e-mail column (punycode domain, provider-specific alias rules) used only for uniqueness and abuse checks.

### F-10 — E-mail recovery inherits domain-expiry takeover risk

- **Category:** Account recovery (residual risk) · **CWE:** CWE-640
- **Severity:** Informational
- **Description:** PR #11 stopped Google sign-in from auto-linking non-Gmail addresses. An attacker who re-registers an expired company domain can still receive the **password-reset e-mail** for accounts on that domain. Every e-mail-recovery system has this property.
- **Remediation:** For organization and moderator accounts later, offer a second factor (TOTP or passkey) and require it for recovery. Show "last sign-in" information to users.

### F-11 — Voice control sends audio to the browser vendor's speech service

- **Category:** Privacy · **Severity:** Informational
- **Affected component:** `web/components/hands-free.tsx` (`SpeechRecognition` / `webkitSpeechRecognition`)
- **Description:** In Chrome and some other browsers the Web Speech API performs recognition on the vendor's servers. The voice recordings of users, possibly parents of children with disabilities, then leave the browser for a third party that the privacy policy does not mention. The feature is user-controlled and off by default, which is good.
- **Remediation:** Disclose this in the privacy policy and in the voice-control panel. Prefer on-device recognition where the browser supports it (`processLocally`).

### F-12 — Dev server reachable from the local network

- **Category:** Security misconfiguration (development) · **Severity:** Low
- **Description:** `next dev` listens on all interfaces (log: `Network: http://192.168.0.186:…`), and `allowedDevOrigins` allows `192.168.*.*`, `10.*.*.*` and `*.local`. Anyone on the same Wi-Fi can use the dev app and its dev database. Dev mail, including reset links, goes to the console, not the network.
- **Remediation:** Bind to `127.0.0.1` by default (`next dev -H 127.0.0.1`) and keep LAN access as an opt-in script (`npm run dev:lan`).

### F-13 — GitHub Actions pinned to mutable tags

- **Category:** CI/CD supply chain · **SLSA:** source/build integrity · **CWE:** CWE-1357
- **Severity:** Low
- **Affected component:** `.github/workflows/ci.yml` (`actions/checkout@v7`, `actions/setup-node@v7`, `gitleaks/gitleaks-action@v3`)
- **Description:** Tags can be moved by the action owner or an attacker who compromises it. Workflow permissions are already minimal (`contents: read`), which limits the impact.
- **Remediation:** Pin to full commit SHAs with a version comment; Dependabot keeps SHA pins updated.

### F-14 — Dependency and runtime versions

- **Severity:** Low / Informational
- `npm audit --omit=dev`: **0 vulnerabilities**. The full tree has 9 moderate entries, all from `minimatch` GHSA-g3hv-75wg-m249 through ESLint (dev only).
- Lockfile: 403 packages, all with `integrity`, all resolved from `registry.npmjs.org`, no install scripts.
- `next` 16.4.5 includes all published 2026 Next.js and React Server Components advisories, including CVE-2026-126187: the fix marker `getBackingBlob` is present in the bundled `react-server-dom-*`. 16.4.6 is available as a bug-fix release.
- Local Node.js 24.18.0 predates the 2026-11-11 security release (24.22.3). CI uses `node-version: 22`, which resolves to the latest 22.x. Pin the production runtime to ≥ 24.22.3 or ≥ 22.23.5.
- No `Math.random` in server code; all secrets and tokens use `crypto.randomBytes`.

### F-15 — CodeQL `js/insufficient-password-hash` (PR #11) — false positive

- **Location:** `web/tests/security.test.mjs:21` (`const sha256 = (v) => createHash("sha256")…`)
- **Analysis:** The flagged data is a random 256-bit reset token created by the test helper `issue()` (`randomBytes(32)`), hashed to look it up the same way the server stores tokens (`lib/auth/tokens.ts`). It is not a password. The heuristic is probably triggered by the purpose string `"reset_password"`. Real passwords are hashed with scrypt (`lib/auth/password.ts`).
- **Action:** Dismiss as "false positive" with that justification, or rename the helper (`tokenHash`) and add a `// codeql[js/insufficient-password-hash]` suppression comment.

### F-16 — Out-of-scope observations (not tested)

Seen while preparing the plan and recorded only so they are not forgotten:

- The repository is **public**. Treat security reports and `.env.example` comments accordingly.
- `main` has **no branch protection**, so `CODEOWNERS` is not enforced and force-pushes are possible.
- Vercel creates **preview deployments** for PRs. Whether they are publicly reachable and which database or secrets they use was not examined. Personal data must stay off Vercel until the legal review (CLAUDE.md).

### F-17 — Compliance and documentation gaps

- No account deletion or data export, and no retention schedule. CLAUDE.md requires these before release.
- The privacy policy is a draft that needs legal review.
- `docs/adr/0001-auth-backend.md` is outdated. It still says rate limiting trusts `X-Forwarded-For`, that Google links by any verified e-mail, and that verification gates nothing.
- No permission matrix for non-auth resources yet; this is needed before moderation, organizations' staff and courses.

### F-18 — HSTS `preload` with `includeSubDomains`

- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` is correct for production. Submitting the domain to the preload list is effectively irreversible for every subdomain, so confirm that all present and future subdomains will serve HTTPS before submitting.

## Verified controls (tested, no vulnerability found)

| Area | Test | Result |
|---|---|---|
| SQL injection | Code review of every query; hostile filter and search values | All queries parameterised; `ORDER BY` from a whitelist; LIKE escaped |
| XSS (reflected, stored, DOM) | Hostile display names, search terms, `?error=`, `?next=`; sink review | React escaping everywhere; one static inline script; `?error=` limited to known keys |
| Open redirect | `//evil`, `/\evil`, `%5C`, `%2F%2F`, absolute URLs, tab, `%09`, U+3000, `javascript:` on `/login?next=` (signed in, production build) | Every target stayed on the same host; unsafe values fell back to `/ru` |
| CSRF / login CSRF | Missing or foreign Origin, `text/plain` form posts, Google form POST | Refused (`403` / `303 → error`); OAuth `state` + PKCE bound to cookie |
| Session management | Fixation, forged cookies, logout, logout-all, suspension, reset | Fresh token per login; server-side revocation works; cookies `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax` in production |
| Access control / IDOR / BFLA | Role from the session only, other users' profiles, self-verification, `/me` | No cross-account read or write; privileged roles not assignable |
| Mass assignment / prototype pollution | Extra fields, `__proto__`, `constructor.prototype` in JSON | Ignored; stored role stayed `parent` |
| Race conditions | 20 parallel uses of one reset token; 10 parallel sign-ups of one e-mail; 20 parallel wrong logins; 12 parallel submit/draft edits | Exactly 1 success; 1 user and 1 session; exactly 8 attempts before `429`; consistent final state (`submitted` with a submit's content) |
| Cache leakage (Cache Components / PPR) | Personalised pages fetched signed-in and anonymously | `Cache-Control: private, no-store`; no e-mail in anonymous output |
| Host header poisoning | `X-Forwarded-Host: evil.example` on pages and on `/forgot` | Not reflected; links are built from `NEXT_PUBLIC_SITE_URL` |
| Path normalisation | Trailing slash, `//`, `./`, case, `..` on protected pages and APIs | No bypass (308 or 404; `/me` stays `401`); soft 404s return a real 404 with `noindex` |
| Error handling | Invalid JSON, 5 000-level nesting, huge numbers, NUL bytes | Generic `400`; no stack traces |
| Request size | 4 MiB chunked body without `Content-Length` | Refused with `400` after at most 32 KiB |
| Headers | Production response | CSP, HSTS, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, COOP, no `X-Powered-By`, no CORS headers |
| Information disclosure | Production source maps | None in `.next/static` |
| Cryptography | Code review | `randomBytes` for all tokens; scrypt (N=2^15, r=8, p=3); `timingSafeEqual`; Telegram HMAC per spec; only hashes of tokens stored |
| Telegram payload | Code review: unknown keys, type confusion, replay, freshness | Unknown keys rejected; HMAC covers the string form, so a type change cannot forge a payload; replay is blocked by `(id, auth_date)` |
