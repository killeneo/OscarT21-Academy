## Executive summary

The fixes from the first audit hold: lint, type check, 94/94 tests on `next dev`, and 60 passed + 2 skipped by
configuration (62 in total) on the production build. `npm audit --omit=dev` reports 0 issues. The production build
sends the expected headers and ships no source maps.

The re-audit found **two confirmed logic issues in the account lifecycle** that the earlier tests missed:

- **R-01 (Medium):** an e-mail confirmation link works without the account owner's session. Someone who signs up with
  a victim's address keeps their password and session once the victim clicks "Confirm". If the victim later signs in
  with Google using that Gmail address, the account is linked to it silently (account pre-hijacking).
- **R-02 (Low; Medium for this product):** sign-up shows whether an address is already registered, through the
  `Set-Cookie` header and through the UI message itself. On an inclusive-education platform, knowing that someone has
  an account is sensitive in itself.

The F-02 fix (Telegram widget) separates pages by **path only**. The browser treats `/ru/telegram` and the rest of
the site as one origin, so the third-party script is still not isolated (**R-03**, potential risk). The other items are
low or informational.

**Overall:** fine for continued MVP development. Fix R-01 before Google sign-in is enabled for real users, and
decide on R-02 and R-03 before launch.

## R-01 — E-mail confirmation works without the owner's session (account pre-hijacking)

| | |
|---|---|
| Category | Authentication / account linking (pre-hijacking, "classic–federated merge") |
| OWASP | A07:2021 Identification and Authentication Failures; ASVS V2.5 / V3 |
| CWE | CWE-287 Improper Authentication; CWE-345 Insufficient Verification of Data Authenticity |
| Severity | **Medium** (High once child or medical data is stored in accounts) |
| CVSS 4.0 | `AV:N/AC:L/AT:P/PR:N/UI:A/VC:H/VI:H/VA:N/SC:N/SI:N/SA:N` (vector only) |
| Affected | `app/api/auth/verify/confirm/route.ts`, `lib/auth/users.ts` (`resolve()`), `components/recovery-forms.tsx` (`VerifyConfirm`) |
| Confidence | High |

**Description.** `POST /api/auth/verify/confirm` marks the token owner's e-mail as verified for anyone who holds the
token. It does not check who is signed in, and it does not end the account's existing sessions. Anyone can create a
password account with someone else's address (R-02 shows this is expected), so:

1. The attacker signs up with `victim@gmail.com` and a password of their choice and keeps the session.
2. The victim gets "Confirm your email" and clicks it (the page shows a single "Confirm email" button). The
   account is now *verified*, and the attacker's password and session still work.
3. Later the victim chooses "Sign in with Google". `resolve()` finds a **verified** account with this Gmail address
   and links the Google identity to it. The protection added in PR #11 (clear the password and revoke sessions) runs
   only for *unverified* accounts, so it is skipped. The victim now uses an account the attacker can also open with
   the password.

Even without step 3, after step 2 the attacker has a *verified* account under the victim's address and can pass the
"confirmed e-mail" gate: send a specialist profile for review, or create an organization in the victim's name.

**Evidence (PoC, both `next dev` and the production build).** Script: `docs/security/poc/poc3.mjs`. The
token was planted in `email_tokens` in place of the mailed link.
```
victim clicks confirm (no cookie): 200 {"ok":true}
after : email_verified_at set = true | attacker password kept = true | role = organization
attacker's session after victim confirmed: 200 {...}
attacker password login: 200 {"ok":true}
```
Step 3 follows from code review: `lib/auth/users.ts:106-117` (the `if (!match.email_verified_at)` branch is the
only one that clears the password and revokes sessions). Not run live, because Google is not configured locally.

**Preconditions.** The victim clicks a confirmation link for a sign-up they did not make. For step 3, the address is
`gmail.com` / `googlemail.com` and the victim later uses Google sign-in.

**False-positive considerations.** It needs user interaction. Step 3 was not run against Google.

**Remediation.**
1. Make confirmation **session-bound**. `verify/confirm` accepts the token only if the request carries a session of
   the same `user_id`. Otherwise the page asks the person to sign in and keeps the token in memory, then retries. The
   victim has no session for the attacker's account, so the link does nothing for them.
2. Defence in depth for linking. When a Google identity is linked to an existing account **that has a password**,
   ask for that password once, or end all sessions, clear the password and send the owner an e-mail notice.
3. Optional: add "If you did not create this account, do not confirm" to the confirmation page, not only to the mail.

**Retest.** Repeat the PoC: the session-less confirm must fail (`401` or `invalid_token`) and `email_verified_at`
must stay `NULL`. With the same user's session it must succeed. Add a unit test for `resolve()`: linking to a
verified password account must not keep the old password or sessions without re-authentication.

## R-02 — Sign-up reveals whether an e-mail is registered

| | |
|---|---|
| Category | Information disclosure / account enumeration |
| OWASP | A07:2021; WSTG-IDNT-04 |
| CWE | CWE-204 Observable Response Discrepancy |
| Severity | Low (technical); **Medium in context**: an account on this platform suggests a child with special needs |
| CVSS 4.0 | `AV:N/AC:L/AT:N/PR:N/UI:N/VC:L/VI:N/VA:N/SC:N/SI:N/SA:N` (vector only) |
| Affected | `app/api/auth/register/route.ts:31-48`, `components/auth-form.tsx:66-70` |
| Confidence | High |

**Description.** For a taken address the route returns the same JSON and status (`201`) as for a new one, and the code
comment says this prevents enumeration. A new account, however, also gets `Set-Cookie: session, device`, and a taken
address gets none. The client then calls `/api/auth/me` and shows the message "this e-mail may already be registered"
(`check_email`). Anyone can learn whether an address has an account, through the UI or with one request.

**Evidence (PoC, dev and production).**
```
new address  : 201 {...} Set-Cookie: __Host-session,__Host-device
taken address: 201 {...} Set-Cookie: (none)
```

**Preconditions.** None. Limited to 10 sign-ups per IP per hour. Probing an unregistered address creates an account
and sends a confirmation mail to that address, so the probe is noisy.

**Remediation (product decision).**
- *Option A (MVP):* accept it as a residual risk, fix the misleading comment, and document it. Sign-in and password
  reset stay non-enumerable.
- *Option B (before launch, recommended for this audience):* e-mail-first sign-up. Always answer "check your mail",
  and create the session only when the mailed link is opened. This also closes R-01 step 1 and R-07.

**Retest.** Responses for a new and a taken address are identical, `Set-Cookie` included.

## R-03 — Telegram widget isolated by path, not by origin (F-02 is mitigated, not fixed)

| | |
|---|---|
| Category | Third-party JavaScript / supply chain (client side) |
| OWASP | A08:2021 Software and Data Integrity Failures |
| CWE | CWE-829 Inclusion of Functionality from Untrusted Control Sphere |
| Severity | Low–Medium (depends on a compromise of `telegram.org`) |
| Affected | `next.config.ts:57-64`, `components/telegram-login.tsx` |
| Confidence | Medium (browser same-origin rules; not exploited) |

**Description.** The F-02 fix serves `telegram-widget.js` only on `/[lang]/telegram`, a page without a password field.
That page is still on the **same origin** as the rest of the site. A modified widget script could:
- show a fake password form or "session expired" prompt on the real domain (phishing that cannot be told apart);
- act as the user with same-origin `fetch` once the Telegram sign-in on that page has created the session: read
  `/api/auth/me`, write `/api/profile/onboarding`, call `logout-all`;
- create a `__Host-google_oauth` cookie with a state and verifier it knows, then send the browser to the Google
  callback with the attacker's code (login CSRF into the attacker's account).

COOP and `frame-ancestors 'none'` stop it from scripting other pages directly, but a path is not a security boundary.
The URL cannot be pinned with SRI, because Telegram changes `telegram-widget.js?22` in place.

**Remediation.** Host the widget on a **separate origin** (for example `tg.<domain>`, a static page that only forwards
the signed payload to the app with a top-level POST), or use Telegram's redirect flow without loading its script on
the app origin. Check the exact redirect parameters against the current Telegram documentation. Until then, keep the
current CSP and COOP split.

**Retest.** No `telegram.org` script on any app-origin page. The Telegram sign-in still creates a session.

> Not verified: whether the widget's `data-onauth` callback needs `'unsafe-eval'` (absent from the production CSP).
> Check the Telegram sign-in on staging before launch.

## Low and informational findings

**R-04 — Token in the query string reaches access logs (Low, potential, CWE-598).** The address bar is cleaned
(F-06), but the first `GET /ru/reset-password?token=…` is still written to the access logs of Vercel, the proxy or the
CDN. A reset token is valid for an hour. *Fix:* put the token in the fragment (`#token=…`, never sent to the server)
and read it on the client, or exchange it for a short-lived HttpOnly cookie on first load. *Retest:* server logs
contain no token.

**R-05 — Inherited keys in `?error=` (Informational, CWE-1321-adjacent).** `auth-page.tsx:480` uses `error in m.errors`,
which is also true for `constructor`, `toString` and similar names. `/ru/login?error=constructor` renders an **empty**
`role="alert"` that screen readers announce. Confirmed by `curl`. No XSS (React escapes the value). *Fix:*
`Object.hasOwn(m.errors, error)`, and the same at `auth-form.tsx:54` and `recovery-forms.tsx:165`.

**R-06 — Site URL fallback (Informational).** `lib/site.ts` uses `http://localhost:3000` when `NEXT_PUBLIC_SITE_URL` is
missing. In production this breaks the OAuth `redirect_uri` and mail links, and `hasSameOrigin` then relies on `Host`
alone. The value is inlined at **build** time. *Fix:* fail fast, as for `TRUSTED_IP_HEADER` (log in
`instrumentation.ts` and refuse auth routes in production when it is unset or not `https:`).

**R-07 — Attacker-chosen role and profile survive the owner's reset (Informational).** After a password reset of a
never-verified account, the owner keeps the role (for example `organization`) and the profile data the pre-registrant
entered. *Fix:* when the first verification or reset happens on a never-verified account, reset the role and
onboarding, or let the owner review them. Option B of R-02 removes the issue.

**R-08 — Telegram accounts skip the e-mail gate (Informational, business logic).** `onboarding/route.ts:27` exempts
accounts without an e-mail. Telegram accounts can create organizations and send profiles for review with no other
trust signal. That is acceptable, because moderation follows, but put a limit on queue volume per account before
launch.

**R-09 — Catalog query cost (Low, potential).** Any signed-in user can run many searches using a leading-wildcard
`ILIKE` over seven columns with `count(*) OVER()` and `OFFSET` up to 11 988, without a rate limit. Not load-tested
(DoS testing excluded). *Fix:* a `pg_trgm` index or full-text search, a per-user limit, and keyset pagination when the
catalog grows.

**R-10 — Dev dependency advisory (Informational).** 9 moderate advisories, all from `minimatch` (ReDoS) through
`eslint` / `typescript-eslint`. Production dependencies: 0. CI (`--audit-level=high`) passes. *Fix:* let Dependabot
bump eslint and typescript-eslint.

**R-11 — Local Node version (Informational, F-14 still open on the dev machine).** `node -v` is 24.18.0. The project
requires ≥ 24.22.3 for the runtime security fixes. CI uses Node 22, which is fine.

## Verified again (no vulnerability found)

SQL injection: every query is parameterised, `ORDER BY` comes from a whitelist, and `LIKE` input is escaped.
XSS: no raw-HTML sinks besides the static script. Open redirect: `safeNextPath` plus a relative `redirect()`.
CSRF: Origin check on every POST, SameSite=Lax, OAuth `state` + PKCE. Session fixation: a new token on every login.
Logout-all and reset revoke sessions. IDOR and BFLA: the role comes from the session, and the catalog shows only
published profiles. Mass assignment and prototype pollution in JSON bodies. Body size limits. Production headers: CSP,
HSTS, XFO `DENY`, `nosniff`, COOP, `no-store` on personalised pages, no `X-Powered-By`. No source maps in
`.next/static`. No secrets in git history (pattern scan; gitleaks runs in CI). `.env.local` is git-ignored.
